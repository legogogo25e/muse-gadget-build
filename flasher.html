Closed loop · Agent development for muse-gadget

  1. Edit codeChanges land in legogogo25e/muse-gadget — the independent development repo (imported from upstream, not a fork). The build workflow now points there.
  2. Actions buildGitHub Actions in muse-gadget-build compiles each board and publishes firmware + manifest.json to GitHub Pages.
  3. Page detectsThis page polls the manifest every 45s, detects each board's chip via esptool-js, and matches it to the right firmware entry.
  4. FlashFlash one board or “Flash all matched”. Every file is SHA-256 verified before writing — a mismatch aborts.
  5. AcceptanceSerial output, boot markers and crash / reboot-loop checks run per board (see lamps below).
  6. Report backIf a report endpoint is configured, results POST automatically after a 10-second observation window — or send manually. That report is what the agent reads to iterate.

Honest limits: Web Serial requires one click per port to grant access — the browser will not let a page claim USB devices silently, so “fully automatic” starts after you add each board once on this computer. Real hardware flashing is not yet verified end-to-end (no USB device on the build side); treat the first run on each board as a supervised test. Use the GitHub Pages top-level copy of this page for real flashing — the muse.ai embedded preview cannot pass the serial permission through.

Auto-report · Send results back

Point this at a small Worker endpoint that creates a GitHub Issue in muse-gadget / muse-gadget-build (that Worker is a separate step — it is not deployed yet). The page POSTs a JSON report: board, detected chip, firmware version / build time, the three acceptance results, per-board multi-board results, and the serial log tail. Nothing is sent anywhere until you paste an endpoint here.

When auto-report is on and an endpoint is set, the report is sent automatically 10 seconds after flashing finishes (the observation window lets the boot / crash checks settle). Endpoint and toggle live in memory only — reload the page and you need to paste it again.

Serial monitor

Only the ROM banner arrived — no firmware boot log The monitor received the ESP-ROM:… line, so the chip did reset and its ROM ran — but no ESP-IDF / application output followed within 6 seconds. That pattern means the app never started logging: it may have halted before ESP-IDF init, or the flashed image may not match this chip. Try: press “Reset device” and watch again; confirm the firmware was built for this board's target chip (see the Firmware card); make sure nothing is holding GPIO0 / BOOT or EN. If the board's LED is breathing (advertising), the app may in fact be running — check for its BLE name with a scanner app such as nRF Connect rather than relying on this monitor alone.

The monitor and the flasher share one serial port — only one can be open at a time. When the device reboots or is replugged, the port can vanish for a few seconds; the monitor fully releases the port and retries with backoff for about 30 seconds, re-attaching automatically if the board re-enumerates as a new USB device.
